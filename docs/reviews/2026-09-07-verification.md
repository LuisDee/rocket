## New problems the remediation introduced

### N1. The `harness-tests` CI job is red — F17's remediation broke it

`.github/workflows/check.yml:120` still runs `uv run --directory tools/strava_probe pytest -q`. That directory was deleted in the same commit that left the line in place. `tasks/strava-withdrawal-and-redlines.md:61-64` predicted this precisely and handed it over as "outside this task's ownership"; nobody picked it up. `docs/ci-gates.md:50` records it honestly in bold — but the row's status is still `IMPLEMENTED`, which under that file's own rules means a promise about mechanism. A job that cannot pass is not an implemented gate. Either the line goes and the status stands, or the status becomes `DISABLED` with a reason until it does.

### N2. The peak long run is exempt from the guardrail built to catch it

`config/training.ts:299` — `if (LIVE_RACE_DATES.includes(session.date)) return [];` — skips the whole session, and week 4's `longRunKm: 33` sits on `2026-10-04`, Lincoln day. The stated rationale is "a race distance was chosen months ago and is not a planner decision to smooth" (`:156-157`). That holds for the 21.1 km of Lincoln. It does not hold for the ~12 km wrapped around it, which the planner chose this week and could change tomorrow. `config/training.test.ts:382` makes the exemption visible: shift the races one day earlier and Lincoln reappears as a 122% breach. So the block's largest single session is unmeasured by the rule introduced to measure exactly that, and the test that would catch a regression here asserts the exemption rather than questioning it. The lazy fix is to net the race distance out of the session before the check rather than skipping the date — the planner-chosen remainder is the part the rule was built for.

### N3. `03-planner.md:28` still enforces a race that was dropped

"Race roles are enforced: Lincoln executed at marathon pace, **not raced; Dorney easy**." Dorney was ratified as dropped on 2026-09-07 and carries `role: 'dropped'` in `RACES`. This is the only live, non-superseded spec line still treating it as a session to place. `06-training-block.md:40` also names it but sits under an explicit SUPERSEDED banner, which is fine.

### N4. The rewritten plan states a fact about itself that is false

`PLAN-2026-001:160` says pillar (b) — thresholds and rules as cited data — is "**The only unstarted pillar.** Grepping `docs/`, `config/` and `src/` for `applied_rules`, `rules table`, `rules registry` or `citation` returns zero hits." The plan rewrite (`54f55a5`) landed _after_ the config commit (`fb2cb6f`) that added `GUARDRAIL_RULE_IDS` and a docstring naming `applied_rules[]` at `config/training.ts:223`. The grep returns hits. The pillar is started; the plan says it is not.

### N5. The plan re-introduces a reference the F17 task withdrew

`tasks/integration-harness.md:19-20` states "the DoHardThings `lib/strava-*.ts` port source is withdrawn as a reference with them". The plan, rewritten afterwards, lists that exact quartet as lift item #3: "the Strava ingest/token/webhook/crypto quartet plus its store triple" (`PLAN:18-38`). One of the two is wrong. (Reading DHT's own source for an ingest-ordering pattern is arguably not "Strava API materials" under §5.3 at all — but the repo now says both things.)

### N6. `05-integrations.md` contradicts itself on the Garmin source

Lines 28-33 still say the source is undecided, "decided by a probe before any schema is designed", with "Field coverage of the bridge is unverified". Line 58, added in the same era, presupposes intervals.icu as the ingest key holder for the outbound leg.
